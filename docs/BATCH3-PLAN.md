## المرحلة A — الفلوس مباشرة (الأخطر)

### A1 — #14: تسوية رصيد العميل مع مجموع الحركات

**المشكلة:** `customer.balance` رقم مخزّن يتعدّل بـ increment/decrement في مسارات متعددة (تأكيد آجل، إلغاء، إرجاع كامل/جزئي، سندات). أي خطأ أو تعديل يدوي = رصيد معروض غلط بدون ما حد ياخد باله.

**التنفيذ:**
1. دالة `computeCustomerBalance(customerId)` في `apps/api/src/services/customer.service.ts`:
   - `SUM(فواتير CONFIRMED آجلة: total - amountPaid)` − `SUM(سندات قبض RECEIPT)` + `SUM(سندات صرف DISBURSEMENT)` على مستوى العميل، مع احتساب المرتجعات (الفواتير `RETURNED` رصيدها صفر بالفعل بعد دفعة 1).
2. Endpoint جديد `GET /api/customers/:id/reconcile` يرجّع: الرصيد المخزّن، الرصيد المحسوب، الفرق.
3. Endpoint `POST /api/customers/:id/reconcile` (ADMIN/MANAGER فقط) يصحّح `balance` للقيمة المحسوبة ويسجّل العملية في الـ Audit Log.
4. تقرير شامل `GET /api/customers/reconcile-all` يعرض كل العملاء اللي عندهم فرق ≠ 0 (شاشة في الإعدادات أو التقارير).
5. منع تعديل `balance` مباشرة من `PUT /customers/:id` (يتشال من الـ validator لو موجود).

**اختبار:** فاتورة آجل 1000 + سند قبض 400 → المحسوب = 600 = المخزّن. تعديل يدوي في DB → التقرير يظهر الفرق → تسوية → تطابق.
**تقدير:** 4–5 ساعات.

### A2 — #7: النقد المتوقع في الوردية يشمل السندات والمصروفات والمرتجعات

**المشكلة:** في `shift.service.ts` الـ `expectedCash = openingCash + CASH payments` فقط. لو الكاشير صرف مصروف من الدرج أو ردّ نقدية لعميل، فرق الإقفال يبان غلط وهو سليم.

**التنفيذ:**
1. توسيع حساب `closeShift` و`getShiftSummary`:
   - `expectedCash = openingCash + مدفوعات CASH − مدفوعات REFUND (لفواتير الوردية) + سندات قبض − سندات صرف − مصروفات نقدية` — كلها المسجّلة **أثناء فترة الوردية** (`openedAt` → الآن) وبنفس المستخدم حيث ينطبق.
2. عرض تفصيلة الحساب في ملخص الوردية (سطر لكل مكوّن) بدل رقم واحد، عشان الكاشير يفهم الفرق منين.
3. حفظ التفصيلة في `CashierShift` (حقول جديدة أو JSON في `notes` مهيكل) — يفضَّل أعمدة: `cashRefunds`, `receipts`, `disbursements`, `expenses` (migration بسيط).

**اختبار:** وردية بافتتاح 500 → فاتورة كاش 1000 → مرتجع جزئي كاش 200 → مصروف 100 → سند صرف 50 → `expectedCash = 1150` والفرق عند الإقفال بـ 1150 فعلي = صفر.
**تقدير:** 4–6 ساعات.

### A3 — #18 (إكمال): توحيد التعامل مع المرتجعات بين التقارير وكشف الصندوق

**المشكلة:** `reports.service.ts` يخصم `RETURNED` بطريقة، و`cashStatement.service.ts` يخصم `REFUND` payments بطريقة — لازم مصدر حقيقة واحد عشان مقارنة اليوم بين Dashboard والتقرير والكشف تطلع نفس الرقم دايماً.

**التنفيذ:**
1. تعريف موحّد مكتوب في الكود (util مشترك `apps/api/src/utils/salesAggregates.ts`):
   - **نقد اليوم** = مدفوعات `CASH` − مدفوعات `REFUND` (زي الكشف حالياً).
   - **صافي المبيعات** = مجموع فواتير `CONFIRMED` بعد خصم قيمة المرتجعات الجزئية (الـ total متعدّل بالفعل) − الفواتير اللي بقت `RETURNED` بالكامل.
2. `getTodaySummary` و`getSalesReport` و`calculateDayData` كلهم يستهلكوا نفس الـ util.
3. **ملاحظة مرتجع اليوم التالي:** فاتورة اتأكدت أمس واترجعت النهاردة — الخصم يظهر في يوم الإرجاع (مش يوم الفاتورة) في الكشف والتقرير معاً.

**اختبار:** سيناريو يوم كامل (بيع كاش + بيع آجل + مرتجع جزئي + مرتجع كامل لفاتورة أمس) → Dashboard = تقرير المبيعات = كشف الصندوق، رقم برقم. يُضاف للسكربت الآلي `scripts/integration-batch2-audit.cjs` أو سكربت `batch3` جديد.
**تقدير:** 3–4 ساعات.

## المرحلة B — سلامة البيانات والمحاسبة

### B1 — #21: Audit Log كامل

**المشكلة:** لا يوجد أي أثر لمن حذف/ألغى/أرجع/عدّل. وده صار أهم بعد قرار #20 (الكاشير يقدر يرجّع).

**التنفيذ:**
1. موديل جديد في `schema.prisma`:

```prisma
model AuditLog {
  id         String   @id @default(cuid())
  userId     String
  action     String   // CONFIRM_INVOICE | CANCEL_INVOICE | RETURN_FULL | RETURN_PARTIAL | DELETE_ITEM | DELETE_CUSTOMER | SETTINGS_CHANGE | BACKUP_RESTORE | RECONCILE_BALANCE | USER_CREATE | USER_ROLE_CHANGE | LOGIN_FAILED_LOCK ...
  entityType String   // SALES_INVOICE | ITEM | CUSTOMER | SETTINGS | USER | BACKUP
  entityId   String?
  detailsJson String? // قبل/بعد أو المبلغ أو المفتاح المتغيّر
  ip         String?
  createdAt  DateTime @default(now())
  user User @relation(fields: [userId], references: [id])
  @@index([entityType, entityId])
  @@index([userId])
  @@index([createdAt])
}
```

2. خدمة `audit.service.ts` بدالة واحدة `logAudit(...)` تُستدعى **داخل نفس الـ transaction** للعمليات الحساسة:
   - مبيعات: confirm / cancel / return / partial-return / حذف مسودة.
   - أصناف وعملاء وموردين: حذف (soft delete) وتعديل سعر التكلفة.
   - إعدادات: أي تغيير قيمة (المفتاح + القيمة القديمة والجديدة).
   - مستخدمين: إنشاء، تغيير دور، إعادة كلمة مرور.
   - نسخ احتياطي: استعادة.
   - أمان: قفل حساب بعد محاولات فاشلة.
3. Endpoint `GET /api/audit` (ADMIN فقط، مع فلاتر: مستخدم/نوع/فترة + pagination).
4. شاشة عرض بسيطة في الإعدادات → «سجل العمليات» (قراءة فقط، ADMIN).
5. **لا حذف ولا تعديل** لسجلات الـ Audit من أي API.

**اختبار:** كل عملية من القائمة تنفَّذ مرة → سجل واحد صحيح بالمستخدم والتفاصيل؛ محاولة `DELETE /api/audit/...` → 404/403.
**تقدير:** 6–8 ساعات.

### B2 — #13: حماية الفواتير المعلّقة (PARKED) من التعارض

**المشكلة:** جهازان يفتحان نفس المعلّقة؛ آخر `PATCH` يكسب والتاني يضيع صامتاً.

**التنفيذ (Optimistic Locking):**
1. الواجهة ترسل `updatedAt` اللي قرأته مع الـ `PATCH /sales/:id` والـ `POST /:id/confirm`.
2. في `updateSalesInvoice` و`confirmInvoice`: الشرط يبقى `updateMany({ where: { id, status: IN(DRAFT,PARKED), updatedAt: <القيمة المرسلة> } })` — لو `count = 0` والفاتورة موجودة → خطأ `409 INVOICE_MODIFIED_ELSEWHERE` برسالة عربية: «الفاتورة اتعدّلت من جهاز تاني — حمّلها من جديد».
3. الواجهة عند 409: زر «تحميل النسخة الأحدث» يعيد جلب الفاتورة.
4. للتوافق الخلفي: لو الواجهة ما بعتتش `updatedAt` (نسخة قديمة) يمر بدون فحص — يتشال التساهل ده بعد تحديث كل الأجهزة.

**اختبار:** جهازان (طلبان API) يقرآن نفس المعلّقة → الأول يعدّل وينجح → التاني يعدّل بنسخته القديمة → 409.
**تقدير:** 3–4 ساعات.

### B3 — #17 (إكمال): تعميم الحماية من سباق خصم المخزون

**الوضع:** التأكيد المتوازي لفاتورتين اتاختبر ونجح (دفعة 2)، لكن `stockOut` في `stock-ops.service.ts` لسه بنمط read-then-decrement (فحص `bal.qty < qty` ثم decrement منفصل) — أي مسار تاني بيستدعيه (تحويل مخازن، جرد، مرتجع مشتريات) معرّض نظرياً لنفس السباق.

**التنفيذ:**
1. تحويل الخصم لعملية **ذرّية مشروطة**:

```ts
const res = await tx.stockBalance.updateMany({
  where: { itemId, warehouseId, qty: { gte: qty } },
  data: { qty: { decrement: qty } },
})
if (res.count === 0) throw new Error(`INSUFFICIENT_STOCK:...`)
```

2. ده يغطي **كل** المستدعين تلقائياً لأنهم كلهم بيمروا على `stockOut` (بيع، تحويل، جرد بالسالب، مرتجع مشتريات).
3. إعادة تشغيل اختبار التزامن (كاشيران، qty=1) + اختبار تحويل مخازن متوازي.

**اختبار:** الموجود في سكربت دفعة 2 + حالة تحويل مخزنين متوازيين على رصيد 1.
**تقدير:** 2–3 ساعات.

## المرحلة D — الفاتورة الإلكترونية ETA (#28) — موديول كامل بمفتاح تشغيل

> **المبدأ:** الموديول يتبني كامل لكن **معطّل افتراضياً**. المحل غير المسجّل في المنظومة يشتغل عادي كأن الموديول غير موجود. التفعيل قرار من شاشة الإعدادات.

### D1 — الإعدادات والتهيئة

| مفتاح | القيمة | ملاحظة |
|-------|--------|--------|
| `eta_enabled` | true/false | **موجود بالفعل** — المفتاح الرئيسي |
| `eta_environment` | `preprod` / `prod` | بيئة تجارب مصلحة الضرائب ثم الإنتاج |
| `eta_client_id` / `eta_client_secret` | نص | من بوابة الممول (تُخزَّن مشفّرة أو في ملف env للجهاز، لا تُعرض بعد الحفظ) |
| `eta_rin` | الرقم التسجيلي للممول | |
| `eta_activity_code` | كود النشاط | |
| `eta_branch_id` | كود الفرع | |
| `eta_pos_serial` | سيريال نقطة البيع | مطلوب لمسار الإيصال الإلكتروني (eReceipt) |
| `eta_doc_type` | `receipt` / `invoice` | **مهم:** محل التجزئة B2C ينطبق عليه غالباً **الإيصال الإلكتروني (eReceipt)** وهو لا يحتاج شهادة توقيع؛ الفاتورة B2B تحتاج توقيع إلكتروني بشهادة |

- قسم جديد في `settings/page.tsx`: «الفاتورة الإلكترونية (ETA)» فيه سويتش التفعيل + الحقول أعلاه + زر «اختبار الاتصال» (يجرب توكن OAuth على البيئة المختارة).
- سويتش التفعيل مقفول (disabled) لو الحقول الأساسية ناقصة، مع رسالة توضح الناقص.
- تغيير أي إعداد ETA يتسجل في الـ Audit Log.

### D2 — التوليد عند التأكيد (Queue)

- في نهاية `confirmInvoice` (داخل الـ transaction): لو `eta_enabled=true` → إنشاء `EtaDocument` بحالة `PENDING` و`payloadJson` مبني من الفاتورة (البنود، الكميات، الأسعار، ض.ق.م 14%، بيانات العميل لو موجودة، بيانات الممول من الإعدادات).
- لو `eta_enabled=false` → لا يحدث شيء إطلاقاً (سطر واحد شرطي).
- المرتجع الكامل/الجزئي على فاتورة سبق إرسالها → مستند `EtaDocument` جديد من نوع إشعار خصم/مرتجع مرتبط بالـ uuid الأصلي.

### D3 — عامل الإرسال الخلفي (Worker)

- خدمة `eta.service.ts` + مجدول بسيط (نفس نمط `startAutoBackupScheduler`):
  1. كل دقيقة: هات المستندات `PENDING` أو `RETRY` (بحد أقصى دفعة 20).
  2. توكن OAuth (client credentials) مع كاش للتوكن حتى انتهاءه.
  3. إرسال حسب `eta_doc_type` (submit receipt / submit document).
  4. نجاح → `status=SUBMITTED` + حفظ `uuid` و`responseJson`؛ رفض → `status=REJECTED` + سبب الرفض؛ خطأ شبكة → `status=RETRY` مع backoff (المحل ممكن يكون النت فاصل — الطابور يستوعب أيام).
- **مبدأ حاسم:** فشل الإرسال **لا يمنع البيع أبداً** — الفاتورة المحلية تتأكد وتتطبع عادي والإرسال يتكرر في الخلفية.

### D4 — الواجهة والمتابعة

- عمود/شارة حالة ETA في قائمة المبيعات وتفاصيل الفاتورة (معلّق / مُرسل / مرفوض) — يظهر فقط لو `eta_enabled=true`.
- شاشة «مستندات ETA» (ADMIN/MANAGER): قائمة بالفلترة على الحالة + زر «إعادة إرسال» للمرفوض بعد تصحيح السبب.
- عدّاد في الـ Dashboard: «X مستند بانتظار الإرسال» لو فيه متراكم.

### D5 — متطلبات خارج الكود (على صاحب المشروع عند التفعيل)

1. التسجيل على بوابة الممولين وأخذ Client ID/Secret وتسجيل نقطة البيع (POS serial).
2. لو المطلوب فواتير B2B: شهادة توقيع إلكتروني من جهة معتمدة.
3. تجربة كاملة على بيئة `preprod` قبل التحويل لـ `prod`.

**اختبار المرحلة D:** مع `eta_enabled=false` كل سيناريوهات القبول الحالية تمر بدون أي سجل ETA. مع التفعيل على preprod (أو mock server محلي في السكربت): تأكيد فاتورة → `PENDING` → worker يرسل → `SUBMITTED` مع uuid؛ قطع الشبكة → `RETRY` ثم نجاح لاحقاً؛ مرتجع → مستند مرتبط.
**تقدير:** 16–24 ساعة (أكبر بند في الدفعة — يتقسم PRs: D1+D2 ثم D3 ثم D4).
